# FEAT-23 — 메인 루프 기록 (게이트 결정·검증 라운드)

## 발주와 게이트① 개방 (2026-08-27)

FEAT-23은 2026-08-26 사용자 관측으로 백로그에 등재된 형제 항목 중 하나다 — 같은 뿌리
("대시보드가 진행 상황을 안 보여준다")에서 FEAT-24는 원격 실행의 실시간 진행(#87 코멘트,
pill 실행 로그)을, FEAT-23은 **항목의 파이프라인 여정 위치**(보드 데이터, 카드 스테퍼)를
맡는다. FEAT-24가 검증 클린 패스로 게이트② 대기에 든 날, 사용자가 세션에서 "계획 승인"으로
FEAT-23의 선정(소유자 직접 발주)과 `계획지시` 전이를 함께 결정했다. 메인 루프가 보드를
편집했고 결정은 사용자의 것이다.

- 병렬 미결: FEAT-24 `검토대기`(검증 클린, 게이트② 대기). 미결 2건은 소유자 결정으로 기록.
- 요구 원천: `TASK_BACKLOG.md`의 FEAT-23 `source`(관측/진단(코드 확정)/설계 시 판단 분리).

admin-dev를 계획서 작성에 디스패치한다. 핵심 판단 지점(계획 단계에서 다뤄야 할 것):

- **단계 모델의 전 경우**: 여정 7단계(선정 → 게이트① → 계획서 → 검증 → 게이트② → 구현 →
  인수)에 대해 status 전 값(승인대기·계획지시·검토대기·구현승인·완료·보류·null)의 매핑을
  결정적으로 정의한다. 특히 **보류**(여정 중단 — 어느 단계에서 멈췄는지 표시할지, 여정 밖
  표기로 뺄지)와 **완료**(인수까지 채울지 — 보드의 `완료`는 dev 기록이고 인수는 메인 루프
  몫이라 보드 데이터만으로 "인수됨"을 알 수 있는지)가 갈림길이다.
- **검토대기 이분**: `검증:` 줄 존재로 "검증 중"과 "검증 통과 · 게이트② 대기"를 가른다
  (백로그 설계 판단, FEAT-13 칩과 같은 신호원 — `board.ts`의 `validation` 필드).
- **게이트①②는 사용자 단계 구분 표시** — "지금 누구를 기다리는지"까지 전달(백로그 요구).
- **데이터 경로**: `briefing.ts`의 `flatten`이 이력 행 dedupe를 이미 하므로 스테퍼도 최신 행
  기준이어야 한다. 순수 매핑 모델은 pages/pipeline `model/`에, 소비는 카드 UI에 — 새 데이터원
  없음(fetch owner 불변).
- **어느 카드에**: 결재함(inbox)과 보고 피드(feed) 카드 양쪽인지, 결재함만인지. 완료·보류
  카드(feed)에 스테퍼가 노이즈인지 정보인지 계획서가 판단한다.
- **반응형**: 폰 카드 폭에서 7단계 스테퍼가 들어가는가 — BUG-07(SVG 스케일 축소로 라벨 판독
  불가)의 교훈: 텍스트를 스케일에 얹지 말 것. 라벨 생략/점만 표시 등 축약 전략을 디자인
  방향에 명시.
- **frontend-design 스킬**: 생김새 변경이므로 A단계 전 로드(admin-dev 정의 규칙), 계획서에
  디자인 방향 절을 남긴다.
